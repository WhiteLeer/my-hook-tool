# HSR 4.5 MuMu Evidence: r111-r116

## Scope

These runs were used to separate MuMu/HSR startup state, native bridge loading,
and the version-checked serialized-field observers. No semantic identity mapping
was accepted from these runs.

## Confirmed

- r111 and r112 did not reach a running HSR Unity process. Their TypeTree wait
  ended with `guestProcess=not_running`; they are startup failures, not ABI
  rejection evidence.
- r113 reached the HSR Unity process, but the Android crash buffer recorded two
  `SIGSEGV` crashes on `UnityMain` at `libunity.so + 0x23bbc0c` during the
  observer-enabled launch. The crash PC was identical in both records.
- r114 used no serialized-field, context, resolver, or identity observer. HSR
  reached the title screen and then an in-world scene without a new HSR crash.
  Its runtime catalog contains concrete Unity class rows, including `Material`
  (class ID 21, size 264) and `Shader` (class ID 48, size 648).
- r115 enabled only the generic serialized-field observer at
  `0x23c87b8` (`0xd103c3ff`). HSR did not produce a UnityMain crash in the
  observed window, but the guest remained at the title/login flow and the
  event file was empty.
- r116 enabled only the Material-field transfer observer at `0x23c77a4`
  (`0xf81a0ffe`). The guest again remained in the title/login flow; the event
  file was empty and no new HSR UnityMain crash was observed before the run was
  stopped.

## Observed

- r111 retained 672 bridge/runtime records and no Unity transfer records.
- r112 retained 141 bridge/runtime records and no Unity transfer records.
- r113 produced no usable Unity event stream before the crash; its generated
  configuration records the external ARM64 bridge mode (`native_bridge_probe_mode=6`)
  and the enabled context/resolve/Material-field observers.
- r114 generated a runtime catalog, but `runtime/events.ndjson` remained zero
  bytes for the sampled period. This is a catalog-only baseline for the tested
  client state, not proof that the transfer observer is semantically correct.
- The active HSR screen after r116 showed the client login network error
  `1001_0`; this prevented a valid in-world Material/Shader workload.

## Hypothesis

- The repeated r113 crash is associated with the observer-enabled external
  bridge path or one of its combined ABI hooks, but the current runs do not
  isolate the exact observer. The identical PC alone does not identify the
  responsible hook.
- The lack of events in r114-r116 is primarily explained by the client not
  reaching a stable authenticated in-world state. It cannot be used to reject
  the field-entry RVAs.
- Static disassembly shows `0x23bbc0c` is an internal Unity table access that
  dereferences a global pointer before hashing/lookup. It is not itself a
  TypeTree or identity boundary.

## Blocked

- No run in r111-r116 produced a same-call Material owner, `m_Shader` field,
  typed Shader return, `sourceFile#PathID`, or RenderDoc EID.
- No observer was accepted or changed based only on event order, thread,
  address, pointer equality, opaque values, or ResourceId.
- The next runtime experiment requires HSR 4.5 to authenticate and reach an
  in-world scene, followed by one observer at a time. The external network
  login state is currently the immediate runtime blocker.

## Decision

Accept r114 as a safe catalog/injection baseline and r115-r116 as incomplete
observer trials. Reject r111-r113 as usable identity evidence. Do not modify
Material/Shader mapping code until a new run reaches an authenticated scene and
produces a non-empty, version-checked event chain.
